Splitting app.js

One 1,301-line script runs the whole documentation SPA: the item catalog, the navigation, the Mermaid renderer, the Construction Status textbook, the git-status poller, and the hash router. Here is what is actually in there, the five structural faults worth naming, and a module split that fixes them in six shippable steps.

Five faults worth naming

Each one is checkable against the current file. The last two have already produced real inconsistencies in shipped behavior.

Navigation state is five loose variables that every layer reaches into

app.js:147–159 · 12 hand-placed renderNav() calls · 6 hand-placed resetConstructionTaskNav() calls

currentTop, itemPath, currentDetail, constructionTaskPath and focusedConstructionTask are module-level lets. filePath() and itemKey() read them implicitly, so their results depend on invisible ambient state. Every command — goHome, selectSection, selectNode, goUp, selectDetail, applyHashRoute — re-implements the same ritual: mutate, reset construction nav, call renderNav(), call showCurrentContent(). Forgetting one line of that ritual is a silent bug with no warning.

Observer A NavState object owns the fields and publishes on change; the nav view and the content host subscribe. The ritual is enforced by the type, not by discipline.

Detail tabs are polymorphic in everything but code

app.js:995, 1117, 1212, 1227 — four functions branching on the same two key strings

detailTabs is a flat list of { key, label, file }, so every tab-specific behavior has to be reintroduced as a string comparison somewhere else: renderNav asks whether the key is "status", selectDetail asks again, applyGitStatusUI asks whether it is "update_docs", and pollUpdateRun asks a third time and then looks the tab back up by string. Adding a sixth tab with any behavior of its own means finding all four sites.

Strategy One object per tab — SourceTab, DiagramTab, ConstructionStatusTab, UpdateDocsTab — each knowing its filename, its after-load hook, and its nav contribution. The four conditionals become four method calls.

Post-injection wiring is a hand-maintained checklist, and it is already out of sync

app.js:164, 478, 362, 402 — four enhancers, three call sites, three different subsets

Any HTML injected into the page needs some combination of executeScripts, renderLessonDiagrams, wireRunTestsButtons and wireProjectTerminalButtons. Nothing enforces which. Today renderCanonicalConstructionLesson runs all four, renderConstructionTextbookTask runs three — it omits wireProjectTerminalButtons — and loadFile runs one. So an inline lesson with an "open a terminal here" button renders the button and leaves it dead, while the same markup in the canonical leaf file works. That is the exact shape of the stale-lesson divergence CLAUDE.md already documents, in a different layer.

Chain of Responsibility over a Composite One ContentEnhancer interface, one ordered pipeline, one applyEnhancers( container ) that every injection path calls. Subsets stop being expressible, so they stop drifting.

The lesson renderer is a 110-line procedure assembling one document

app.js:757–868 — renderConstructionTextbookTask

Masthead, status badge, copy-path button, edition line, trail sentence, key-idea callout, cloned authored sections, child roster table, progress counts, a "has the author already written a continuation?" DOM query, chapter numbering, footer, script execution, diagram rendering, and button wiring — all in one function body, in one linear sequence, with no seam to test or reuse a piece.

Builder new ConstructionLessonBuilder( task ).masthead().keyIdea().authoredSections() .roster().counts().continuation().footer().build(). Each step is independently readable and independently skippable; the pipeline stays the one place that knows the order.

The relative-URL invariant is enforced by a comment, eight times

app.js:379, 418, 456, 508, 1033, 1101, 1175, 1199

CLAUDE.md is explicit that a leading slash on api/git-status breaks the SPA under the dashboard's /agent-block/ reverse proxy — and the current defense is a prose comment at the call sites that happen to have one. The same eight sites also re-decide cache: "no-store", JSON-vs-text parsing, and error shape independently, which is why a failed git-status silently becomes { exists: false, dirty: false } in one place and a rendered error string in another.

Facade, with a Null Object A single DocsApi module owns every server route and is the only file allowed to call fetch. Relative-path correctness becomes one line in one file. The unknown-status fallback becomes a named UNKNOWN_STATUS constant instead of two duplicated literals.

Proposed module layout

Native ES modules, no build step — the SPA's no-toolchain constraint holds. app.js shrinks to a composition root: it constructs the concrete objects, wires the subscriptions, and starts the router.

Two collapses worth calling out

  • wireRunTestsButtons and wireProjectTerminalButtons (app.js:362 and 402) are the same 35-line algorithm with different selectors and labels. They become one asyncActionButton( spec ) factory and two six-line specs — a Template Method where only the varying parts are written down.
  • Ten constructionTask* helpers each re-derive their answer from raw DOM with Array.from( children ).find( … ). As one Task Adapter with title(), description(), children(), ancestors(), siblings(), they become the first thing in this codebase that is unit-testable without a browser.

Migration sequence

Ordered by risk, lowest first. Each step is a self-contained commit that leaves the SPA working — per the repo's commit-before-you-stop rule, none of these should sit uncommitted across a session.

  1. Extract the pure datano logic moved

    sections, detailTabs, overviewFile, DOC_ROOT, MERMAID_THEME move out verbatim. Immediately worth it on its own: sections is one of the three places CLAUDE.md says every new leaf must be registered, and adding one stops producing a diff against the same file as every behavior change.

  2. Extract the pure functionsno state touched

    doc-tree.js, task-model.js, hash-route.js parsing. These take arguments and return values — no content, no nav, no globals. This is where a first test file becomes possible.

  3. Introduce DocsApimechanical

    Move all eight fetch sites behind named methods. Fixes the duplicated-fallback inconsistency and puts the reverse-proxy invariant in one place where a future reviewer can actually find it.

  4. Build the enhancer pipelinebehavior change, intended

    One ordered chain, called from every injection path. This deliberately changes behavior: wireProjectTerminalButtons starts running on inline lessons, where it is currently missing. Worth verifying in headless Chrome through the real nav flow, per the skill's diagram-verification workflow.

  5. Split the Construction Status subsystemlargest diff

    405 lines out, into the Builder plus the task-nav module. Behavior-preserving, but it is the biggest single move — and the Construction Status pages are the ones with the most authored content depending on their exact rendering.

  6. Replace the globals with NavStatetouches everything

    Last, because every earlier step reduces the number of call sites that read the globals directly. Tab Strategies land with it, since they need somewhere to subscribe. Do this one alone, in its own commit.

Open questions for the team

Cache-busting does not survive the split as-is

index.html versions exactly one file (app.js?v=20260902hashroute2), and that query string is the SPA's only cache control. Static import specifiers inside modules are fetched and cached independently — so after the split, a bumped entry-point version would still serve every stale submodule. Three options: append ?v= to every import specifier (mechanical but noisy and easy to half-do), reintroduce a concatenation step (rejected by the no-build-step constraint), or send Cache-Control: no-store for .js from server.py. The server header is the recommendation — we own the server, it is roughly five lines, and it removes a manual step that is currently easy to forget.

Is any of this testable, and do we want it to be?

There is no test suite here and nothing to lint; verification means driving headless Chrome through the real nav flow. Steps 1–3 produce genuinely pure modules — path resolution, hash parsing, task-tree queries — that a plain Node script could assert against with no DOM at all. That is a decision to make deliberately: the split's main payoff is only collected if we take it.

Does the item catalog want to stay in JavaScript?

sections in app.js, the folder on disk, and resolve_source_path() in doc_source_map.py are three hand-synced registries, and mazda/ is already half-registered — navigable, but with git status and Update Documentation silently dead. Once sections is its own file, publishing it as JSON that both app.js and the Python side read is a small step, and it would let a checker script catch that class of drift. Out of scope for this refactor; worth deciding whether we are heading there.
